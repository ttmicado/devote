# スクレイピング基盤 アーキテクチャ調査

> 2026-10-13 にサブエージェントが調べた結果をまとめたもの。法的な検討は対象外。実装状況は `docs/architecture.md` を参照。

## データの流れ
```
Scheduler → list ジョブ →（詳細URLを見つける）→ detail ジョブ → raw_snapshot 保存
  → parse → normalize → listings upsert → 差分検知 → 名寄せ → properties 更新
  → change_events → マッチング → 通知
```
**取得（fetch）と解釈（parse）を分ける**のが要点。生HTMLを保存しておけば、パーサを直したあと過去分を再パースできる。

## 取得方式の使い分け
| サイトの条件 | 方式 |
|---|---|
| SSRの静的HTMLで、値がHTMLに含まれている | cheerio（HTTPで取得）。高い並列度で回せる |
| SPAだが内部のJSON APIを特定できる | HTTPでJSONを直接取得する（ブラウザは使わない） |
| JSでの描画が必須、多段フォーム | Playwright（画像・フォントは `page.route` でブロックする） |
| ログインのときだけJSが必要 | **Playwrightでログイン → storageState のcookieを使ってHTTPで取得**するハイブリッド |

## ログインセッション（会員サイト）
- アカウントごとに storageState を暗号化して保存する。`isLoggedOut()` でセッション切れを検知したら、分散ロック（`pg_advisory_lock`）を取ってから再ログインする
- **同時実行は1アカウントにつき1**。2FAやCAPTCHAが出たら自動では進めず、`needs_human` にして運用者に通知する

## レート制御・リトライ
- ドメインごとのトークンバケット（全ワーカーで共有）。指数バックオフ＋ジッタ
- 429/503 が返ったらレートを一時的に半分にする。404/410 はリトライせず「掲載終了の候補」にする
- サーキットブレーカー: 失敗率が閾値を超えたら、そのソースを一時停止してアラートを出す

## キュー
- 初期は **pg-boss**（Postgresだけで完結し、トランザクションの中でジョブを投入できる）
- 規模が大きくなったら BullMQ(Redis) に移す。そのために `JobQueue` インターフェースで抽象化しておく

## 差分検知
- `change_events.type ∈ new | price_down | price_up | field_changed | delisted | relisted`
- **掲載終了の判定**: 一覧を最後のページまで正常に巡回できた回だけ数え、連続2〜3回見つからない、または詳細ページが404/410なら delisted にする（途中で失敗した回は数えない）
- 一覧から取れる値のハッシュ（listHash）が前回と同じなら、詳細の取得を省略する

## スナップショット
- gzip をオブジェクトストレージ（R2/S3）の `/{source}/{yyyy}/{mm}/{dd}/{sha256}.html.gz` に置く。DBにはメタデータだけ持つ
- ハッシュを取る前に、CSRFトークンやタイムスタンプなどのノイズを取り除く
- `parserVersion` を上げたら、`raw_snapshots` を再パースするジョブを投入する（サイトへの再アクセスは不要）

## 名寄せ
1. 住所を正規化して緯度経度を付ける → 2. ブロッキング（町丁目、半径100m） → 3. スコアリング（面積±0.5㎡、階、間取り、築年月、建物名の trigram 類似度、価格差、pHash） → 4. 高スコアは自動で統合、中間は人がレビュー、低スコアは別物件 → 5. `merge_log` を残して統合を取り消せるようにする

## スケジューリング
- **収集の頻度と通知の頻度は完全に分ける**（両者は `change_events` だけでつながる）
- 目安: 会員系・業者間サイトは一覧を30〜60分ごと（営業時間帯）、大手ポータルは2〜6時間ごと、中小の自社サイトは1日1回、掲載終了確認のための全件巡回は深夜に1日1回

## 構造変化の検知とテスト
- 一覧が0件なのに総件数が1以上、件数が前回から50%以上減った、必須項目の充足率が落ちた、DOMの指紋が変わった → **掲載終了の判定を自動で止めてアラートを出す**
- フィクスチャHTMLでスナップショットテストをする。本番でパースに失敗したHTMLをフィクスチャとして取り込むCLIを用意する
- 実サイトに当てる canary テストを日次で回す

## 実行環境
| 候補 | 月額の目安 | 備考 |
|---|---|---|
| **単一VPS**（4〜8vCPU / 16GB） | 3千〜1.5万円 | 最安。IPを固定できるので会員サイトと相性が良い |
| Cloud Run Jobs + Cloud SQL | 1〜4万円 | IPを固定するには Cloud NAT が必要 |
| ECS Fargate + RDS | 2〜8万円 | 中〜大規模向け |

**推奨する初期構成**: VPS 1台 ＋ マネージドPostgres（Neon/Supabase）＋ R2。
