# Devote プロジェクト考察と進め方

> キャッチコピー: **あなたにピッタリ合う物件を、最速で・手間なく・くまなく提案してくれるAI**
> 出典: 2026-10-13 のミーティング議事録（Notion）と依頼内容。調査の詳細は `docs/research/` にある。

## 1. 解決したいペイン

| ユーザーの不満 | 原因（業界構造） | Devote の解 |
|---|---|---|
| 良い物件はポータルに出た時点でもう決まっている | 元付 → レインズ → 客付が見つける → ポータル入稿、という**多段のラグ** | 上流（業者間サイト・自社サイト）を直接巡回して**最速**で届ける |
| 毎日ポータルを見るのが面倒 | 条件検索が5千円刻みなど粗く、通知も弱い | AIが条件を覚え、指定した頻度で**手間なく**届ける |
| 自社サイトにしか載らない物件を取りこぼす | レインズに載せない会社がある | 自社サイトも巡回して**くまなく**拾う |
| 条件をうまく言語化できない | 「70㎡以上」と「69.5㎡もOK」の違いは営業との対話でしか詰められない | 営業担当を再現したAIと**壁打ち**する |

## 2. 考察（重要な論点）

1. **賃貸の鮮度はレインズより業者間サイトの方が高い。** 賃貸はレインズへの登録が任意のため、ATBB／ITANDI BB／いい生活スクエアなどの業者間サイトや、管理会社の業者向けページの方が早く・多く出る。巡回対象を「レインズ＋業者間サイト＋自社サイト（＋網羅用のポータル）」の**三層**で考えるべき。
   → 最初に決めること: 対象を賃貸と売買のどちらから始めるか、どのエリアか。
2. **「最速」の価値を最大化するには、巡回頻度と通知頻度を分けて設計する。** 巡回は30〜60分ごと、通知はユーザーが選んだ頻度にする。人気の賃貸物件は数日で申込みが入るため、「即時」通知を選べるようにし、通知文に掲載からの経過日数を表示する。
3. **Instagram DM は定期プッシュに使えない。** Meta の24時間メッセージングウィンドウの制約で、ユーザーからDMが来てから24時間以内しか送れない。議事録にある「広告 → 条件登録 → DM通知」の導線は、次のように修正するのが現実的。
   - Instagram: **集客の入口**と**会話型**の利用に絞る。ユーザーが「新着ある？」とDMしたら即座に返す
   - 定期通知: **LINE（メイン）とメール**で行う。DMの中でLINEの友だち追加へ誘導する
4. **名寄せが品質を決める。** 同じ部屋が複数のサイト・複数の業者に載るため、名寄せをしないと同じ物件が何度も通知される。listings（掲載）と properties（実物件）の2層で持ち、通知は property 単位で送る。
5. **境界のすぐ外の物件が差別化になる。** ポータルの刻みでは漏れる「予算＋3千円」「69.5㎡」を、許容幅つきのスコアリングで拾い、「0.5㎡狭いですが…」と理由を添えて提案する（`packages/core/src/matching.ts` に実装済み）。
6. **「対応不可 → 類似物件」は学習データの蓄積が本体。** 最初は管理者が判断し、類似候補・判断・ユーザーの反応をすべて記録する（`similar_suggestions` テーブル）。承認率が安定した判断パターンから順にAIで自動化する。
7. **内見問い合わせの客付可否確認は自動化の余地が大きい。** 広告可否・AD・取引態様は客付できるかのシグナルになる。業者間サイトの空室確認APIで、問い合わせの前に確認できる可能性がある。

## 3. 進め方（フェーズ）

### Phase 0: 土台づくり（← 今回）
- [x] 要件の整理とドメイン調査（サブエージェント3体で並行して調査）
- [x] モノレポ（TypeScript / pnpm）、DBスキーマ、マイグレーション
- [x] 正規化ユーティリティ、ルールベースのマッチング、名寄せキー
- [x] スクレイパーのアダプター基盤と、リファレンス実装（フィクスチャによるテスト）
- [x] Claude Code 用のスキル・サブエージェント・SessionStart フック

### Phase 1: 身内テスト用 MVP（← 2026-10-13 実装。デプロイ待ち）
決定事項（2026-10-13）: 賃貸・売買の両方／対象エリアは港区・中央区勝どき・渋谷区・千代田区・品川区・江東区豊洲／
通知は LINE（フリープラン）とメールのみ／Vercel + Neon + Anthropic で運用。
巡回: 住友不動産ラ・トゥール（2サイト）・森ビル・REIT FIND（rf12）・ケン・コーポレーション・アクセルホーム は稼働、
レインズ・ATBB・ITANDI BB は認証情報の受け渡し後に画面を確認して仕上げる（`docs/member-sites.md`）。

当初計画:
議事録のアクション「まず身内でテストしてみる」に対応する。
1. **巡回対象サイトの決定**（ユーザーと一緒に決める）→ 優先度の高い3〜5サイトのアダプターを実装する
2. 収集パイプライン: pg-boss のスケジューラ → crawl → listings の upsert → change_events → 名寄せ（ルールベース）
3. AIチャット（Next.js + Claude API の tool use）: 条件の壁打ち → 確認カード → 条件の保存
4. マッチング → **LINE通知**（Flex Message）と**メール通知**（Resend）
5. 管理画面（最小限）: 問い合わせ一覧、ステータス変更、「対応不可」にしたときの類似物件候補の表示
6. 運用: VPS 1台 ＋ マネージドPostgres

### Phase 2: 磨き込み
- 埋め込み類似度を加えたハイブリッドスコア、ゲージのUI
- 名寄せの精度向上（pHash、レビュー画面）、構造変化の検知とアラート
- Instagram を入口にした導線（DMの自動返信 → LINEへの誘導）
- 内見予約のフロー（Devote 独占）

### Phase 3: 自律化・拡大
- 類似物件の自動判断（管理者の承認データで学習）
- 対象エリアとソースの拡大、BullMQ やコンテナ基盤への移行
