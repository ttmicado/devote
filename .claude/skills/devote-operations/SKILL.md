# 運用状況の把握と変更の監査

運用の約束（不変条件）と現在の状態は `docs/operations.md` にまとめてある。**最初に必ず読む。**
この手順の目的は「当初の計画を壊す変更」と「本番で起きているエラー」を、別環境の作業のあとでも素早く見つけることにある。

## 1. 状況を把握する（作業の最初に毎回）

1. `docs/operations.md` の §4「現在の状態」と §5「決定の記録」を読む。
2. 最新を取得し、前回の監査以降に入ったコミットを一覧する。
   ```bash
   git fetch origin
   git branch -r                                   # 既定ブランチ（現在 claude/amazing-ride-b7fwem）と作業中の枝
   git log --oneline <最後に監査したコミット>..origin/<既定ブランチ>   # §4 に書いてある
   git diff --stat <最後に監査したコミット> origin/<既定ブランチ> -- . ':!**/__fixtures__/**' ':!**/__snapshots__/**'
   ```
3. マージされていない枝も確認する。`git log origin/<既定>..origin/<枝>` を見て、古い土台の枝は競合を確かめる（`git merge --no-commit --no-ff` で試し、`git merge --abort` で戻す）。
4. 本番の巡回の状態を確認する（§3）。

## 2. 変更を監査する

差分を `docs/operations.md` の §3「要注意の変更」の分類に当てはめ、該当するものだけ深く読む。特に次の点を見る。

- **会員サイトの課金・回数**
  - 1回の巡回でのレインズの検索回数 ＝ 希望条件の範囲（エリア数、ログの「会員サイトの検索範囲: N 件」）× 物件種別（`REINS_KINDS`）。件数事前確認は無料で、0件なら検索しない。
  - 1日の上限 ≒ (4,500 − 今月の使用量) ÷ 月末までの日数（`quota.ts` の `allowanceForRun`）。詳細も同じ式で、今日の分を朝の1回で使い切るのが通常の動き。
  - ITANDI BB は1日3回・5ページまで。ATBB は検索回数のプラン上限があり、残り回数は §4 に書いてある。
- **時間**
  - 新しいソースの初回の取り込み量（詳細の件数）× 1件の所要時間（`rateLimit.minIntervalMs`。詳細1件で複数リクエストを出すサイトはその分を掛ける）を見積もる。
  - 1ソースの持ち時間は15分、全体は42分。
- **壊れ方**
  - parseList / parseDetail が1行の解釈失敗で throw していないか。throw せずに `skipped` を返すか、対象外として除外するのが正しい。
  - 掲載終了の判定を誤らないか。
  - 価格など値の範囲（bigint の列でも、正規化で「億」を誤っていないか）。
- **公開範囲・写真**
  - `memberOnly` の付け忘れ（`registry.test.ts` が Web 側の写しとの一致を確かめる）。
  - 他社のロゴが入った写真（`noImageSourceIds`）。
  - レインズの画像。
- **DB スキーマ**: push した時点で本番に入る（`migrate.yml`）。古いコードでも動くか、ロック時間は問題ないかを確かめる。
- **検証**: `pnpm typecheck && pnpm lint && pnpm test` が既定ブランチで通るか。DB の結合テストは、ローカルの Postgres を `pnpm db:up` で起動し `pnpm db:migrate` をしてから実行する。

## 3. 本番の巡回を確認する（GitHub Actions）

- GitHub MCP（`mcp__github__actions_list` の `list_workflow_runs`、resource_id `crawl.yml`）または `gh run list -w crawl.yml` で、直近の実行の conclusion を見る。
  - **cancelled が続く**: 55分の制限時間で強制終了されている。持ち時間の仕組みが効いているか、ソースが増えすぎていないかを調べる。
  - **failure**: crawl ジョブのログの末尾を見る。
- crawl ジョブのログ（`mcp__github__get_job_logs`、tail 60〜120行）は、ソースごとに1行の JSON（`{"source":…}`）になっている。
  - `ok:false` と `error` が毎回同じなら、データか実装の問題。1回だけなら一時的な問題。
  - `skipped` の主な理由:
    - 提供時間外
    - 前回から○分経っていない
    - 前回「…」で止まったため HH:MM まで待機
    - 本日分の検索枠を使い切った
    - 巡回全体の時間切れ（次回）
  - `deferred` と warnings の「詳細 N 件は件数上限／時間切れのため次回に取得」が回を追って減っていくか。減らなければ追いついていない。
  - warnings の「一覧の巡回が不完全…掲載終了判定をスキップ」が毎回出るソースは、掲載終了が永久に判定されない。原因を直す。
- notify ジョブのログの `{"due":…,"sent":…,"failed":…}` で、通知が出ているかを確認する。

## 4. 報告と記録

- 報告は「計画を壊す・エラーにつながる（要対応）」「方針どおりで問題ない」「軽微」に分け、根拠（ファイル:行、ログの行）を添える。課金・回数は計算式と数字で示す。
- 直したら、または状態が変わったら、`docs/operations.md` を更新する。
  - §4: 現在の状態と「最後に監査した main のコミット」
  - §5: 決定の記録（日付・何を・なぜ）
  - 新しい約束ができたら §2、要注意の変更の種類が増えたら §3
- 本番の DB・会員サイトに影響する操作（マイグレーションの push、会員サイトへのログイン・検索）は、課金と人の作業への影響を考えてから行う。会員サイトの検索はこの手順の確認のためにはしない（ログと DB の記録で判断する）。
